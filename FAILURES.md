# Known Edge Cases & Failures

1. **Rate limit memory loss on restart:** The rate limiter uses an in-memory `request_timestamps` list to enforce the 10 requests / 60 seconds limit. If the FastAPI process is restarted, this memory is wiped. The app will assume it has full capacity and immediately fire 10 requests, which will breach the mock API's rate limit if requests were sent just before the restart. It will correctly handle the resulting `429` errors and backoff, but the breach still occurs.
2. **Duplicate check race condition:** To prevent duplicate DMs for the same user and rule, we check the `RuleExecution` table. However, if two comments from the same user arrive at the exact same millisecond, they might both pass the `scalar_one_or_none()` check before either transaction commits. Both would queue a DM. 
3. **Inflated `duplicates_blocked` on retry:** If the process crashes after a `DMTask` is queued and `RuleExecution` is committed, but before the `WebhookEvent` status is updated to `processed` (or if it fails during the commit of the webhook processing transaction but the DB somehow partially commits—though SQLAlchemy handles this), redelivering the same webhook will see the `RuleExecution` exists and increment `duplicates_blocked`. This means our reported `duplicates_blocked` might be higher than the actual number of true duplicate comments we received.
4. **Reconciler starvation:** The `delivery_reconciler_loop` polls up to 10 `accepted` tasks at a time. If the mock API has a bug where a subset of DMs get permanently stuck in the `queued` state on their end (never reaching `delivered` or `failed`), our reconciler will continually poll those same 10 tasks forever. Other `accepted` tasks might never get reconciled because the stuck tasks occupy the entire 10-item limit.
